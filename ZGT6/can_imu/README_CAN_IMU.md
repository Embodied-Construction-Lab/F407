# CAN IMU 接收与 OLED 显示

目标芯片以本工程的 `can_imu.ioc`、启动文件为准：STM32F407ZGT6。

## 当前接线和设置

- CAN1：PA11=RX、PA12=TX，经过外部 CAN 收发器接 IMU 的 CANH/CANL；共地，总线两端终端电阻按实际设备配置。
- CAN1：经典 CAN、500 kbit/s（PCLK1=42 MHz，Prescaler=6，BS1=11 TQ，BS2=2 TQ）；如果 IMU 速率不是 500 kbit/s，必须修改 CubeMX 配置并重新生成代码。
- 接收标准数据帧 ID `0x121`，过滤器接 FIFO0，启用 CAN1 RX0 中断。
- I2C2：PF1=SCL、PF0=SDA，100 kHz；SSD1306 128x64，驱动探测 7 位地址 `0x3C` 或 `0x3D`。I2C2 外部上拉、电源与实际接线需核对。

## 数据格式及重要假设

`imu.png` 定义 66 字节 IMU 原始帧，帧头 `AB 54 65 00`；Roll/Pitch/Yaw 在偏移 11/15/19，Gx/Gy/Gz 在 23/27/31，均为小端 IEEE-754 float。角度单位 deg，角速度单位 deg/s。

目前没有串口转 CAN 模块的分包协议或抓包。本实现**暂按 CAN ID 0x121 的各帧 DATA 原样、按顺序拼接**。若模块在 DATA 中加入序号、长度、起止标记，必须先在 `CAN_IMU_Process()` 去除或按序重组；若改成多个 ID 分别承载测量量，则需直接实现对应 CAN 协议。CAN ID 属于 CAN 帧头，不会拼入 IMU 原始字节流。

OLED 先在内存中排版 8 行，再每 25 毫秒经 I2C2 更新其中 1 行；这样接收主循环通常不会被一次全屏传输长时间占用。显示初始化仍需要一次全屏清屏。

解析器查找 `AB 54 65 00` 帧头，累计完整的 66 字节后解码；超过 2 秒的 CAN 帧间隔会清空未完成的拼接，500 毫秒没有新的完整测量值时屏幕显示等待状态。队列溢出时也会清空拼接并等待重新同步。因缺少 CRC 参数，不能把当前的帧头同步视作完整的数据有效性验证。

协议图只写“CRC16（覆盖 0–63 字节）”，未给出多项式、初始值、输入/输出反射和最终异或。因此当前代码**没有验证 IMU 内层 CRC16**，仅依赖 CAN 帧硬件校验、连续帧头和有限浮点值检查；这些检查不能替代正确的 CRC16 校验。拿到协议参数后应补上 CRC 校验，再用于需要可信 IMU 数据的控制逻辑。

## 验证边界

已用 ARM GCC 对工程全部 HAL、Core 源码和启动文件完成链接；用主机合成报文覆盖跨 8 字节分片、字段偏移和无效浮点过滤。尚未验证 CAN 分包、IMU 实际报文、I2C 电气连接和 OLED 实物显示。收到连续抓包后先确认 `0x121` 的 DLC、DATA 顺序和每条原始帧的边界，再烧录联调。

CubeIDE 工程编译 `Core` 与 `Drivers`。项目根目录原有 `imu_parser.c/h` 和 `imu_oled_format.c/h` 是旧版参考文件，正式实现位于 `Core/Src` 与 `Core/Inc`；独立编译时不要混用根目录旧文件。
