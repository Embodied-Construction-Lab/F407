# Timer_teleoperate

This project reuses the `truck/remote_control` JSON command parsing, button
override, ESC reverse state machine, 300 ms control timeout, neutral
failsafe, and ST7789 TFT status display. PWM is generated by STM32 TIM1
instead of PCA9685.

## Configuration and wiring

The configured MCU is STM32F407ZGT6. With the configured 8 MHz HSE and
168 MHz system clock, TIM1 receives 168 MHz. `PSC=167`, `ARR=19999` gives a
1 MHz counter and 50 Hz PWM. TIM1_CH1/PE9 is steering, TIM1_CH2/PE11 is
lift, and TIM1_CH3/PE13 is drive. A CCR value of 1500 means a 1500 us high
pulse every 20 ms. All three channels start at neutral (1500 us).

USART1 uses PA9/TX and PA10/RX at 115200 8N1. DMA2 Stream2 receives JSON
lines, and the USART1 global interrupt handles idle detection and transmit
completion. Connect the Jetson bridge to these pins, not the USART2 pins of
`remote_control`. The incoming JSON format is unchanged, for example:

```json
{"type":"logi_raw","steering":0,"throttle":1,"brake":1,"up":0,"down":0}
```

Terminate each command with `\n`. Button-only updates such as `{"up":1}`
are supported. The reply retains the original `pwm` array but its values are
now microseconds, with `"pwm_unit":"us"`; `"timer":1` reports that PWM
channels started. `"i2c":0` indicates that PCA9685 is not used.

The reused control mapping treats the throttle pedal as forward drive and
the brake pedal as a reverse-drive request, not as a neutral brake command.
Confirm that this matches the connected ESC and operator controls before
enabling the drive motor. The configured lift range can reach 600-2400 us;
reduce it if the connected actuator requires a narrower range.

I2C2/PF0(SDA),PF1(SCL) is used for an optional SSD1306 OLED. The ST7789 TFT
uses the same wiring as `remote_control`: SPI3 SCK/PB3, MOSI/PB5, CS/PD11,
DC/PD12, backlight/PD13. The previous SPI3 PC10/PC12 mapping is replaced.
The TFT driver is write-only; a lit display does not prove that its data
lines or the PWM outputs are electrically correct. I2C1 is not used by this
application. The TFT display is included, but the `remote_control` project's
PA1 steering-angle ADC is not, because this project's `.ioc` does not
configure ADC1. Add it only after confirming the sensor wiring.

The TFT shows USART1 DMA status and RX events, valid/invalid JSON counts,
queue drops, age and field mask of the last valid command, mapped control
percentages, target pulse widths, and TIM1 CCR register values. `TIM1:ON`
and matching CCR values confirm software state only, not the physical pin
voltage or actuator power.

## Bench validation

Keep the vehicle actuators disconnected for the first test. Build and flash
the new project, then confirm that PE9, PE11, and PE13 each have a 20 ms
period and a 1.5 ms neutral high pulse. Check the TFT's `U1`, `JSON`,
`AGE`, `PWM`, and `CCR` rows while sending valid JSON frames. At neutral,
motors are intentionally stopped; steering commands must change PE9 pulse
width, the lift buttons PE11, and throttle/brake PE13. Then verify that loss
of valid commands for more than 300 ms returns all three outputs to neutral.
With the actuators disconnected, a complete neutral frame should show
`PWM S:1500 L:1500 D:1500`. `steering:1` should produce about 1833 us on
PE9, `up:1` about 2400 us on PE11, and pressed throttle (`throttle:-1`,
`brake:1`) about 1700 us on PE13. These are software expectations, not
evidence that the actuator has received a valid electrical signal.
Only connect the steering servo and ESCs after checking their permitted
signal voltage, pulse-width range, power supply, common ground, and ESC
arming behavior. A correct MCU PWM waveform alone does not prove the
actuator has power or accepts 3.3 V control-high level.
