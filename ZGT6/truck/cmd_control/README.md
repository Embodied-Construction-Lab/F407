# cmd_control

This project receives the preprocessed `bridge.py` command protocol. It
retains the button override, ESC reverse state machine, 300 ms control
timeout, neutral failsafe, and ST7789 TFT status display from
`Timer_teleoperate`. PWM is generated by STM32 TIM1 instead of PCA9685.

## Configuration and wiring

The configured MCU is STM32F407ZGT6. With the configured 8 MHz HSE and
168 MHz system clock, TIM1 receives 168 MHz. `PSC=167`, `ARR=19999` gives a
1 MHz counter and 50 Hz PWM. TIM1_CH1/PE9 is steering, TIM1_CH2/PE11 is
lift, and TIM1_CH3/PE13 is drive. A CCR value of 1500 means a 1500 us high
pulse every 20 ms. All three channels start at neutral (1500 us).

USART1 uses PA9/TX and PA10/RX at 115200 8N1. DMA2 Stream2 receives JSON
lines, and the USART1 global interrupt handles idle detection and transmit
completion. Connect the Jetson bridge to these pins, not the USART2 pins of
`remote_control`. `bridge.py` sends vehicle steering degrees, signed throttle,
brake request, and optional lift buttons, for example:

```json
{"type":"truck_control","steering":15,"throttle":0.5,"brake":0,"up":0,"down":0}
```

`steering` is -30..+30 degrees (0 means a 90-degree servo command),
`throttle` is -1..+1 (negative means reverse), and `brake` is 0..1 (any
positive value forces neutral drive). A motion frame may omit `brake`, `up`,
or `down`; omitted fields are neutral for that frame. A frame with only
`steering` or `throttle` is also accepted, but other motion fields then return
to neutral. Separate button-only updates such as `{"type":"button","up":1}`
temporarily override the lift state for 300 ms while motion frames continue.
Raw `type:"logi_raw"` frames are rejected to prevent unit confusion.
Terminate each command with `\n`. The reply retains the `pwm` array but its
values are microseconds, with `"pwm_unit":"us"`; `"timer":1` reports that
PWM channels started. `"i2c":0` indicates that PCA9685 is not used.

The project-local `bridge.py` converts a forward pedal into positive throttle,
a reverse pedal into negative throttle, and both pedals into a brake request.
It defaults omitted reverse and lift-button inputs to released. The current
firmware caps drive command at +/-20% and lift command to +/-50%; confirm
that these match the connected ESC and operator controls before enabling the
drive motor. The configured lift range can reach 1000-2000 us;
reduce it if the connected actuator requires a narrower range.

I2C2/PF0(SDA),PF1(SCL) is used for an optional SSD1306 OLED. The ST7789 TFT
uses the same wiring as `remote_control`: SPI3 SCK/PB3, MOSI/PB5, CS/PD11,
DC/PD12, backlight/PD13. The previous SPI3 PC10/PC12 mapping is replaced.
The TFT driver is write-only; a lit display does not prove that its data
lines or the PWM outputs are electrically correct. I2C1 is not used by this
application. PA1 now reads the steering potentiometer through ADC1 channel 1. See the
feedback contract below; the original TIM1 and USART1 wiring is retained.

The TFT shows USART1 DMA status and RX events, valid/invalid JSON counts,
queue drops, age and field mask of the last valid command, mapped control
percentages, target pulse widths, and TIM1 CCR register values. `TIM1:ON`
and matching CCR values confirm software state only, not the physical pin
voltage or actuator power.

## Bench validation

Keep the vehicle actuators disconnected for the first test. Build and flash
the new project, then confirm that PE9, PE11, and PE13 each have a 20 ms
period and a 1.5 ms neutral high pulse. Check the TFT's `U1`, `JSON`,
`AGE`, `PWM`, and `CCR` rows while sending valid JSON frames. At neutral,
motors are intentionally stopped; steering commands must change PE9 pulse
width, the lift buttons PE11, and throttle/brake PE13. Then verify that loss
of valid commands for more than 300 ms returns all three outputs to neutral.
With the actuators disconnected, a complete neutral frame should show
`PWM S:1500 L:1500 D:1500`. `steering:30` should produce about 1833 us on
PE9, `up:1` 2000 us on PE11, and forward `throttle:1,brake:0` 1700 us on
PE13. Negative throttle requests reverse through the ESC's existing
nonblocking transition state machine. These are software expectations, not
evidence that the actuator has received a valid electrical signal.
Only connect the steering servo and ESCs after checking their permitted
signal voltage, pulse-width range, power supply, common ground, and ESC
arming behavior. A correct MCU PWM waveform alone does not prove the
actuator has power or accepts 3.3 V control-high level.

## Measured steering feedback (2026-10-28)

Firmware ID after this source change: `cmd-zgt6-tft-adc-3`. ADC1/PA1 samples nominally every 20 ms;
conversion polling is nonblocking, with a 5 ms conversion timeout. Status is
sent every 100 ms on the existing USART1, including while waiting for commands.
No second serial connection or new actuator control loop is introduced.

Telemetry adds `timestamp_ms`, `feedback_valid`, `sensor_steering_deg`,
`current_steering_deg`, `control_steering_deg`, `steering_adc_raw`,
`steering_voltage_mv` and `steering_sample_age_ms`. The first two angle sensor
fields are physical ADC-derived values in degrees. `control_steering_deg` and
the legacy `steering_deg` remain mapped command values, never measurements.
Startup, conversion failure, rail samples (0/4095), or sample age over 100 ms
give `feedback_valid:0` and both measured angles `null`. A floating/disconnected
sensor can still produce a non-rail value; this is not full sensor-fault detection.

The conversion constants in `Core/Inc/steering_feedback.h` are copied from the
sibling `truck_control`: 3.3 V reference, 12-bit ADC, 1630 mV center, and
0.1 degree/mV, clamped to +/-30 degrees (1330/1930 mV). These are UNVERIFIED
for this vehicle. Validity means a fresh non-rail ADC conversion, not proven
calibration or mechanically accurate road-wheel angle. Confirm voltage range,
center, slope, direction and travel on hardware before relying on the angles.
PA1 input must stay within the permitted MCU analog voltage range.

RLcar already recognizes `feedback_valid` + `sensor_steering_deg`; no ROS
protocol change is needed. Its configured feedback sign is -1.0 and offset is
0.0 degrees, both still requiring physical confirmation. Feedback does not
automatically make the existing PID controller use steering feedback or add
a steering-angle inner loop. It only supplies measured telemetry.

Downlink stays newline-delimited `type:truck_control`, steering in degrees,
signed throttle [-1,1], brake [0,1]. `TRUCK_DRIVE_MAX_PERCENT` remains 20 as a saturation limit;
fixed throttle 0.15 maps directly to drive +15% and an expected 1650 us
TIM1_CH3 pulse. Throttle values above 0.20 remain capped at 20% drive.
Positive brake requests neutral, not active mechanical braking. No change to
the 300 ms control timeout, ESC reverse sequence, or lift-button overrides.

Build includes the copied ST HAL ADC/ADC_EX sources and headers. CubeIDE's
Core and HAL source folders include the new C files; refresh/rebuild the
project if an old generated Debug makefile is present. `cmd_control.ioc`
also records ADC1 and PA1 so regeneration retains the peripheral configuration.
This source change requires a fresh firmware build and flash. Until the board
reports `cmd-zgt6-tft-adc-3`, its 0.15 input still uses the old +3% / 1530 us
mapping. The Jetson test configuration already requires
`cmd-zgt6-tft-adc-3`, so it rejects the old board firmware until the new
image is flashed and verified. No board flash is implied by editing these
sources.
